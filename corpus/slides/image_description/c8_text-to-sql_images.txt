[第3頁, 圖片1] Text-to-SQL 的基本範例，包含一個自然語言輸入區與對應的 SQL 查詢輸出區。自然語言輸入為 "Show me all employees from the Sales department."，下方的灰色程式碼區塊顯示對應的 SQL Query：SELECT * FROM employees WHERE department = 'Sales';，其中 SQL 關鍵字（SELECT、FROM、WHERE）以綠色與紫色語法高亮標示。此圖用於說明 Text-to-SQL 技術如何將日常語言自動轉換為結構化的資料庫查詢語句。

[第5頁, 圖片1] 介紹基於規則與模板方法中的 Data Dictionary（資料字典），以表格形式呈現資料庫結構資訊。表格包含四個欄位：Field Name、Data Type、Description 與 Example，列出三筆欄位記錄：full_name（Text 型別，學生全名，範例 Bob）、contact_no（Text 型別，學生聯絡電話，範例 0912345678）、curr_address（Text 型別，學生現居城市，範例 Khulna）。此表格說明 Data Dictionary 如何儲存資料庫結構資訊以協助 Text-to-SQL 系統理解表、欄位及其關聯關係。

[第6頁, 圖片1] Context-Free Grammar（CFG，上下文無關文法）在 Text-to-SQL 中的應用，包含三個視覺元素。左側為 CFG 文法規則定義表，列出 PERSONAL-INFO 與 CONTACT-INFO 等非終端符號及其展開規則（如 ROLL_、FULL_NAME、F_NAME 等欄位的對應自然語言表達）。右上方為範例自然語言查詢 "Show the student's name and contact no who lives in Khulna."，以紅色標記關鍵詞。右下方為 SQL 語法樹（Parsing Tree），根節點為 SQL_Query(S)，分支為 Select_Node、From_Node 與 Where_Node，逐層展開至具體的欄位名稱（FULL_NAME、CONTACT）、表名（students）與條件（CURR_ADDRESS = 'Khulna'）。此圖說明如何使用遞迴規則生成語法樹來解析自然語言並轉換為 SQL。

[第7頁, 圖片1] Rule Base（規則庫）的概念，以表格形式呈現 SQL 生成規則。表格包含四個欄位：Rule ID、類型、語意模式與對應 SQL 結構。列出三條規則：R1 為選擇欄位類型，語意模式 "show the {column_list}" 對應 SELECT {columns}；R2 為查詢表格類型，預設 students 表對應 FROM students；R3 為地點條件類型，語意模式 "lives in {curr_address}" 對應 WHERE curr_address = '{curr_address}'。此表格說明規則庫如何儲存各種 SQL 生成規則，根據查詢類型自動應用對應的 SQL 結構。

[第8頁, 圖片1] 基於 Data Dictionary 和規則庫組裝 SQL 句子的完整流程。上方為自然語言查詢 "Show the student's name and contact no who lives in Khulna."，其中 student's name 和 contact no 以紅色標記，lives in Khulna 以黃色標記。左下方為灰底的 SQL 語法樹，根節點 SQL_Query(S) 分支為 SELECT_Clause、FROM_Clause 與 WHERE_Clause，分別展開為 full_name 和 contact_no、students、以及 curr_address = 'Khulna'。右下方為深色背景的最終 SQL 輸出：SELECT full_name, contact_no FROM students WHERE curr_address = 'Khulna';，SQL 關鍵字以不同顏色高亮顯示。此圖完整示範了從自然語言到語法樹再到 SQL 語句的轉換過程。

[第11頁, 圖片1] 深度學習方法的缺點，包含資料庫表格與錯誤 SQL 查詢的範例。左側展示兩個資料表：employees 表格（含 id、name、department_id、salary 四個欄位，各有四筆資料如 Alice/50000、Bob/45000 等）與 departments 表格（含 id、department_name 兩個欄位，列出 Engineering、HR、Marketing 三個部門）。右側為紫色粗體的自然語言問題 "List the names of all departments and the salaries of all employees in their department."，下方的 SQL 查詢中 FROM 子句錯誤地使用了 staff（以紅圈標記）而非正確的 employees，並以紅字標註正確應為 employees e 以及需要 JOIN departments d ON e.department_id = d.id。此圖說明深度學習模型在未見過特定資料庫結構時可能會錯誤選擇表名。

[第17頁, 圖片1] Text-to-SQL 的實作流程圖，分為三個階段，由左到右以圖示與文字說明。第一階段 Question Understanding 以人物對話圖示呈現，負責將使用者的自然語言轉換為語義表示；第二階段 Schema Comprehension 以資料庫打勾圖示呈現，負責識別資料庫中的表格和欄位；第三階段 SQL Generation 以長條圖圖示呈現，負責產生正確且可執行的 SQL 查詢。下方以虛線框展示完整範例：左側為 JSON 格式的中間語義表示（包含 select、where、order_by 結構），中間為問句關鍵詞片段與資料庫欄位名稱的對應表（員工姓名對應 full_name、工作經驗對應 job_exp、資料表名稱假設為 employee_info），右側為最終生成的 SQL：SELECT full_name FROM employee_info WHERE job_exp > 5 ORDER BY job_exp DESC;。此圖說明 Text-to-SQL 從問題理解、Schema 理解到 SQL 生成的完整三階段流程。

[第25頁, 圖片1] BIRD 資料集中 Large and Realistic Database Values 的範例。上方深青色標題區顯示 "Large and Realistic Database Values"，下方呈現一個對話式範例：使用者（商務人士圖示）提問 "What is the average salary of the worst performing managers?"，其中 average salary 以粉色標記。AI（機器人圖示）回應一段含有資料型別轉換的 SQL 查詢：SELECT AVG(CAST(REPLACE(SUBSTR(T1.salary, 4), ',', '') AS REAL)) FROM employee AS T1 JOIN position AS T2 ON T1.positionID = T2.positionID WHERE T1.performance = 'Poor' AND T2.positiontitle = 'Manager'。下方為 Reasoned Database 區域，展示 Employees 表格，包含 em_id、last_name、first_name、salary 四個欄位，salary 欄位以粉色邊框標記，資料值為 US$57,500.00、US$19,500.00、US$69,000.00 等含有貨幣符號的格式。左下方註記說明需將包含特殊字符的薪水從字串轉為浮點數。此圖說明 BIRD 資料集中真實資料庫值的處理挑戰。

[第26頁, 圖片1] BIRD 資料集中 External Knowledge Reasoning 的範例。頁面分為兩個對話式範例，皆以深青色背景呈現。第一個範例中使用者詢問 "List account id who chooses weekly issue issuance statement?"，External Knowledge 方框提示 'POPLATEK TYDNE' stands for weekly issuance（捷克語的每週發行），對應 SQL 為 SELECT account_id FROM account WHERE account.frequency = 'POPLATEK TYDNE'。第二個範例中使用者詢問 "How many accounts are eligible for loans in New York City?"，其中 eligible for loans 以虛線框標記，External Knowledge 說明 The condition of loans is that the type of the account should be "OWNER"，對應 SQL 為 SELECT COUNT(*) FROM account WHERE account.type = 'OWNER' AND city = 'NY'。左下方紅字註記強調要求模型能夠推理出哪些帳戶是有資格獲得貸款的。此圖說明 BIRD 如何要求模型利用外部知識進行推理。

[第52頁, 圖片1] XiYan-SQL 的整體流程架構圖，以紅色虛線框劃分為四個主要階段（標號1至4）。第一階段 Schema Linking：包含 Column Retrieval、Column Selector、Value Retrieval 三個子模組，從使用者輸入中取出 column 及 entity 並整理成 M-Schema。第二階段 Candidate Generation：多個 Generator 平行運作，每個 Generator 產生不同風格的候選 SQL 語句（如 SELECT MAX(T1.'Free Meal Count (K-12)' / T1.'Enrollment (K-12)') FROM... 等），每條候選 SQL 都經過對應的 Refiner 檢查錯誤。第三階段 Candidate Selection：收集所有經過 Refiner 修正的候選 SQL，使用 fine-tuned 模型進行最終選擇。第四階段 Final Response：輸出最符合原句語意的 SQL 碼。下方四點文字說明各階段功能。此圖完整呈現了 XiYan-SQL 從 Schema 理解到多生成器候選產生再到最終選擇的端到端架構。
